# Загрузка приложения бригадира

Списки и сводки используют общий Future на 30 секунд: перерисовка, поиск и возврат назад не создают повторные запросы. Успешное изменение данных, вход/выход и ручное обновление главной очищают кэш; ошибочный запрос можно повторить сразу. Кэш ограничен 128 ключами и разделён по аккаунтам. Параллельные запросы с истёкшим токеном обновляют сессию один раз; сетевое ожидание ограничено.

При открытии бригадира показаны его машины и переход к полному списку. Сервер ограничивает выборку обычного бригадира до чтения финансовых данных; итоговая проверка области видимости сохраняется.

Массовое чтение назначений и договорных номеров не загружает полные графики. Остатки графиков агрегируются в PostgreSQL. Для переплаты и одобренных переносов используется прежний расчёт; интеграционный тест сравнивает пакетный и поштучный результат, включая частичную оплату и перенос.

Проверка: `manager-performance.integration.test.ts`, только отдельная БД `gopark_contract_test` с `REPAIR_INTEGRATION=true`. 300 активных водителей, 300 машин, 324 000 ежедневных начислений; статистика PostgreSQL обновлена после заполнения. В облачной тестовой среде: 10 машин обычного бригадира — около 0,16 с; 300 машин и водителей старшего — около 1,1 с на список; сводка — около 2 с; список с выбранным периодом оплаты — около 1,1 с. Это проверка объёма данных при одном читателе, а не 300 одновременных пользователей и не гарантия времени на рабочем сервере. Все записи тестовые, удаляются вместе с временной БД; рабочая база не используется.
