# CRM loading improvements (2026-11-24)

Routes load their page code on demand, while the navigation stays visible. Firebase push code also loads separately. The initial JavaScript entry decreased from 1,490,170 bytes to about 250 KB (about 81 KB gzipped). This is a bundle-size comparison, not a guarantee of an equivalent change in complete page load time. Nginx compresses text/JSON and caches hashed static assets; HTML revalidates so updates use new bundle URLs. A failed section download provides an explicit reload button rather than automatically discarding unsaved input.

API GET requests share a pending promise per authenticated session and URL. Recently opened data can be shown immediately on navigation, but every mounted query still requests fresh server data. Snapshots stay only in memory for up to 15 seconds, are bounded to 128 URLs, and are invalidated before and after mutations and on account changes. Live chat/notification/outbox reads and next-contract-number reads do not retain snapshots. Refreshing a query preserves its visible data and ignores responses from older paths or disposed views. Parallel expired requests share one bounded session refresh. Independent manager summary/driver-list reads run concurrently without changing financial formulas.

Validation: typechecks/build, isolated ReadCache regression tests, existing manager financial tests, and Chromium with intercepted synthetic API responses (100 ms response latency). Browser scenarios covered navigation between users/STO/parts, 20 identical concurrent reads producing one request, one refresh for 10 expired requests, mutation invalidation, account isolation, and stale hook responses. A cached return to STO was approximately 100 ms in this fixture. Production timing depends on database work, user data, device and network; the fixture is not a concurrent-user load test. No synthetic records were written to production.
